# v128 성공 기록과 실기 패키지의 호환성 검토

검토일: 2026-10-21. 원본 시뮬 작업과 이전 현장 패키지는 읽기만 했다. 아래 원본 값은 이식 여부를 판단하기 위한 근거이며, 현장 보정값이나 실기 명령 기본값이 아니다.

## 확인한 성공의 범위

| 항목 | v119 원본 | v128 원본 |
|---|---:|---:|
| 실행 이름 | `native-roas-table-scatter-speed-v119-parallel-445` | `native-roas-table-scatter-speed-v128-closer-transfer-445` |
| 초기 무작위 배치 seed | 445 | 445 |
| 최초 촬영부터 유지 확인까지 wall 검증 시간 | 52.301107초 | **43.533159초** |
| 별도 `cycle_time_s` | 52.285072초 | 43.518469초 |
| 시뮬 물리 경과 시간 | 31.679167초 | 24.789583초 |
| 전체 조립 / 비전 종단 성공 | true / true | true / true |
| 30초 미만 | false | false |
| 실제 하드웨어 시험 | false | false |

두 기록의 `state`는 모두 `completed_over_budget`다. 43.533초는 **시뮬의 실제 wall clock 검증 결과**다. CPU 카메라·인식 대기를 삭제하거나 시뮬 물리 경과 시간 24.790초를 전체 작업 시간으로 표시한 수치가 아니다. v119 대비 wall 시간은 약 8.768초 줄었다. 각 실행은 한 seed의 성공 근거이며 여러 무작위 배치에서의 실기 반복 성공을 뜻하지 않는다.

v128 최종 부품 위치 오차는 링1 약 0.272mm, 링2 약 0.191mm, 핀 약 0.704mm였다. 이 역시 시뮬 내부 최종 판정 값이다. 핀은 명목 8mm 축을 7.6mm의 간이 충돌 형상으로 모델링했고 반경 방향 0.2mm 여유를 사용했다. 실제 끼움 공차를 입증한 결과로 사용할 수 없다. 핀 클램프 높이도 원본에서 실기 보정 미확인으로 표시되어 있다.

근거: 각 실행의 `pipeline-results.json`, `trial-config.json`, `code-manifest.json`과 `code_snapshot/`. 새 패키지의 v128 원본 자료는 `stabilization/v128/`에서 확인한다.

## 인식 코드를 바꿔야 하는가

원본 v119와 v128의 다음 파일은 바이트가 같았다.

- `rgbd_scattered_rings.py`, `rgbd_geometry.py`
- `rgbd_initial_fast.py`, `rgbd_fast_tracker.py`
- `process_vision.py`, `realtime_camera_worker.py`

따라서 v128 호환화를 위해 링 검출 임계값이나 RGB-D 기하 인식을 다시 작성할 이유는 없다. 버전 이름만 보고 인식 코드를 바꾸면 검증된 동작을 불필요하게 흔들 수 있다. 원본 코드 해시, 패키지에서 필요한 import 경로 수정, 실제 카메라 입력·좌표 보정의 경계만 명확히 관리한다.

실기 어댑터는 같은 검출 코어를 사용할 수 있지만 원본의 모든 시뮬 추적 경로와 동일하지는 않다. 원본의 pin axial-end tracker, CAD 기반 빈 지그 깊이 렌더, 가상 카메라 관점 탐색을 실제 센서의 측정 결과로 표시하면 안 된다.

## v128에서 실제로 달라진 전략

| 변경 | 원본에서 확인한 내용 | 실기에 가져갈 방법 |
|---|---|---|
| 작은 링 전달 위치 | 승인된 물체 중심이 약 `(.05019,-.45020,1.34997)`에서 `(-.04981,-.40020,1.39997)`m로 이동 | 가까운 전달 구역을 현장 좌표로 실측·검토한다. 원본 world 좌표를 로봇에 복사하지 않는다. |
| IK 분기 선택 | 현재 관절 자세에 가까운 수신 팔 분기, 작은 회전의 주는 팔 자세를 우선 검색 | 현장 모델과 양팔 충돌 검사 아래 후보를 선택한다. 해당 휴리스틱을 실제로 구현하지 않았다면 이식 완료로 표시하지 않는다. |
| 큰 링 수신 파지 | 수신 파지 후보 `(0,0,0,.004)`를 우선 정렬 | 실제 손·링의 접촉 관계를 측정한다. 4mm 값을 그대로 실물 파지 깊이로 적용하지 않는다. |
| 집기 접근 | pregrasp 높이 바닥 1.185→1.235m, 작은 링 별도 높이 설정 | 접근·상승 경유점과 바구니 턱·다른 부품 여유를 실측한다. 절대 Z 값은 이관하지 않는다. |
| 접촉 하강·손 속도 | 하강 0.06→0.03m/s, 손 모터 상한 0.040→0.032m/s | 실제 Franka Hand의 파지 유지·미끄럼·개방 결과에 따라 정한다. 시뮬의 손가락별 30N과 SDK 파지력 명령은 같은 설정이 아니다. |
| 경로 시간 배분 | 새 `path_local_timing.py`, 확인된 경로의 국소 속도 제약과 스무딩 | 현장 경로에 새 연속 한도 검사·추종 오차·실제 제어 응답 검증이 필요하다. 원본 고속 궤적을 재생하지 않는다. |
| 핀 작업 공간 확보 | 빈 왼팔의 가까운 park 후보, 링 운반 중 양 TCP 거리 0.24m 미만이면 핀 시작 대기 | 현재 양팔 전체 형상·설치 부품·운반 물체 검사로 확보한다. TCP 거리 하나를 충돌 안전 증명으로 쓰지 않는다. |
| 작업 겹침 | `parallel_transfer_approach=false`지만 마지막 링 삽입과 오른팔 핀 작업은 겹칠 수 있음 | 현장 어댑터의 순차 양팔 실행을 유지한다. 동시 경로 검증 없이 시뮬의 동작 겹침을 켜지 않는다. |

v128에서 `warm_spline_routes=false`, `pin_between_rings=false`, `pin_first=false`였다. 새 소스에 기능이 존재한다는 이유로 이 성공 실행에서 사용했다고 표시하지 않는다. `stability_finish_rings_before_pin=false`이므로 '마지막 링 전체 완료 뒤에만 핀 시작'과도 다르다.

현장 엔진은 현재 실측·관측 목표와 검토된 구역에서 실제 SDK 모델로 경로를 만들고, 단계별 확인 후 순차 실행한다. 이 경계를 유지하면서 v128의 작업 순서·새 관측을 통한 파지 관계 G 보정·전달 후 재확인·직접 핀 조립이라는 정책을 참조할 수 있다. **원본 근거를 v128 프로필에 결합하는 것과 v128의 모든 검색·시간 최적화 코드를 실기로 이식하는 것은 별개의 완료 조건**이다. 개별 v128 경로 최적화가 미이식 상태라면 43.533초와 같은 실행 시간은 약속하지 않는다.

## 카메라: 원본이 실제로 사용한 관점

실행 진입점 `run_realtime_recipe.py`는 `process_vision.Vision`을 사용한다. 이름이 비슷한 `realtime_vision.Vision`의 예시 설정만 보고 실제 관점을 설명하면 잘못될 수 있다.

| 원본 역할 | 이미지 크기 | 관점 생성 방식 | 현장 의미 |
|---|---|---|---|
| 초기 바구니 | 640×400 | 바구니 floor + `(.40,-.12,.65)`m에서 floor + `(0,0,.025)`m를 봄 | 바구니 전체와 모든 느슨한 부품이 들어오는 실제 외부 보정이 필요 |
| 접근 전 링 | 192×192 | 관측 물체/로봇 자세에 맞춰 위치와 시야를 새로 계산 | 실제 고정 카메라가 해당 자세에서 링 면을 보는지 확인 |
| 오른손 운반·전달 | 192×192 | 예측 파지 물체 중심 + 관측 요청의 eye offset. 기본 `(.18,-.18,.08)`m, 요청별 변경 가능 | 관점이 물체를 따라 움직이는 가상 카메라를 고정 실물 카메라 한 대로 간주하면 안 됨 |
| 왼손 운반·삽입 | 192×192 | 기본은 예측 물체 중심 + `(-.25,.12,.20)`m. 요청별 관점 변경 가능 | 전달·삽입 구역에서 반대면·지그 가림을 포함해 실제 시야 검증 |
| 핀 홀더 | 256×256 | 원본 eye `(.19,-.79,1.35)`m, target `(.19,-.79,.916)`m | 실제 홀더 위치와 핀 끝면이 보이는 관점을 따로 보정 |

위 좌표는 모두 **원본 시뮬 world 좌표의 설명**이며 현장 설치 수치가 아니다. 최초 프레임의 실제 저장된 `T_cell_camera` 광학 중심은 `(0.951639,-0.845524,1.739882)`m, `K`는 `fx=fy=1093.354834`, `cx=319.5`, `cy=199.5`였다. 실제 RealSense에 이 K를 입력하면 안 된다. 센서 SDK가 해당 해상도에서 제공하는 실제 보정값을 사용한다.

192×192 프레임에서도 저장된 fx는 약 481, 599, 665, 826, 1059 등으로 달랐고 광학 중심도 이동했다. 이 기록은 한 개의 고정 시야·고정 광학 중심을 사용한 카메라 설치 근거가 아니다. 원본 역할을 실제 고정 카메라들의 검증된 시야로 나누거나, 같은 실제 카메라가 같은 외부 보정으로 여러 역할을 담당할 수 있음을 측정해야 한다. 현재 어댑터는 같은 serial의 카메라를 서로 다른 미구현 이동 외부 보정으로 재사용하는 것을 거부한다. 수동으로 카메라를 옮긴 뒤 이전 보정을 그대로 사용하는 방식도 자동 사이클에 포함할 수 없다.

v128은 43.533초 동안 촬영·인식 요청 31회(초기 2, 접근 전 링 4, held 11, held_left 13, 핀 초기 1)를 기록했고 그중 8회에 인식 오류가 있었다. 원본은 관점을 바꾸어 다시 측정한 뒤 성공했다. 이 수치는 센서 FPS가 아니다. 물리 제어 480Hz·시뮬 960Hz도 카메라 FPS나 실제 FCI 검사 주기와 혼동하지 않는다. 실제 카메라에서 같은 오류 복구가 가능하려면 사용 가능한 다른 고정 시야 또는 별도로 구현·보정된 이동 카메라가 있어야 한다.

카메라 배치·보정의 실제 명령 순서는 새 패키지의 카메라 설치 안내를 따른다. 역할별로 확인할 것은 바구니 전체, 손에 잡힌 링의 부호가 있는 면, 받는 손 접근 중 가림, 삽입 전후 지그와 핀 끝면이다. 보이지 않는 영역은 비어 있다고 가정하지 않고 보수적 점유 형상 또는 새 바구니 관측으로 처리한다.

## 새 패키지가 보존해야 하는 경계

1. v128 성공 보고서·trial 설정·원본 코드와 현장 엔진 해시를 함께 고정한다. 다른 실행 자료를 혼합하지 않는다.
2. `experimental_sim_only`, `hardware_tested=false`, `hard_realtime_controller_validated=false`와 핀 형상 여유를 기록에서 지우지 않는다.
3. 현장 recipe·양팔/TCP/카메라 보정·실제 손과 부품 형상·지그 신호는 현장 데이터로 채운다. 원본 actor ID·정답 좌표·시뮬 joint trace는 센서 입력으로 들어가지 않는다.
4. 전체 로봇/손/케이블·운반 부품·이미 설치된 부품·새 프레임의 다른 느슨한 물체를 검사한다. 전달 대상만 새로 보고 나머지 장애물은 오래된 프레임으로 검사하지 않는다.
5. 실제 네이티브 실행기의 추종 오차 한도와 충돌 부풀림 한도를 일치시킨다. 더 촘촘한 한도는 실제로 시행되고 현장에서 시험한 값만 쓴다.
6. 소프트웨어 오프라인 통과, 원본 시뮬 성공, 현장 연결, 실물 세 부품 완주, 실측 전체 시간을 별도로 기록한다.
